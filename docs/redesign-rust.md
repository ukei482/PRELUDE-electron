# PRELUDE 再設計: Rust への移行(設計判断の記録)

状態: **草案**。決まったもの: 1-a(同じリポジトリ)、3-a(Chromium 1 つ + CDP)、5(`.prelude` = スペース 1 つ、TOML)、5-a(ポータルを実装)。
残り: **判断 2(GPUI か Slint か)** — 段階 4 までに決める。

## 0. 目的

もっと使いやすく、ミニマルで、拡張しやすいものにする。そのために次の 4 つを変える。

1. 本体を Electron(JS)から **Rust** に移す
2. ブラウザを PRELUDE から切り離す。Web は **Chromium そのもの** にして、PRELUDE はそれを決まった形で取り込む
3. サイドバー・ファイラなどの UI の部品を **抽象的に記述** する。見た目と実装は使用者が付け替えられる
4. `.prelude` を **スペース(= 1 つのプロセス)1 つ** にし、パス(開く・保存・コンソール…)を持たせる

KDE に任せる範囲(KWin・ロック画面・電源など)は今と同じ([shell-design.md](shell-design.md) の 1 章)。

## 判断 1: 全体の構成 — 「コア」と「UI」を分ける

```
┌─ prelude-core(Rust・常駐) ───────────────────────────┐
│ 状態: スペース / タブ / 分割 / ペイン / .prelude          │
│ OS:   KWin(窓の取り込み・配置)、Chromium の制御、       │
│       ファイル操作・監視、D-Bus(通知・トレイ・OSD・音量)│
│ 公開: コマンドとイベント(下の「UI の約束」)            │
└───────────────▲───────────────────────────────────────┘
                │ UI の約束(Rust の trait / 同じ形の JSON)
┌───────────────┴───────────────────────────────────────┐
│ UI(付け替えられる) 既定の UI = 部品の組み合わせ       │
│ バー / ナビ(スペース・ブックマーク) / タブ / ペインの枠 │
│ ファイラ / ランチャー / 通知 / OSD / クイック設定        │
└───────────────────────────────────────────────────────┘
```

- コアは画面を持たない。**状態の持ち主** で、UI は状態を表示してコマンドを送るだけ
- 今の `fileops.js` の冒頭に書いた「OS に近い部分は将来 Rust に置き換える」をそのまま広げた形
- コアと UI の間は、まず **同じプロセス内の trait** で始め、同じ形を JSON にして Unix ソケットへ出せるようにしておく(外部の UI・スクリプトから操作できる。`prelude` コマンドもこれを使う)

**決めること 1-a: 同じリポジトリか、新しいリポジトリか**
- おすすめ: **このリポジトリに Cargo のワークスペース(`crates/`)を足す**。Electron 版は Rust 版が日常の用途を満たすまでリリースとして残し、満たした時点で消す。`.prelude` の形式とテストを両方で確かめられる
- 案: 新しいリポジトリ(`PRELUDE` の名前に戻す、など)

## 判断 2: UI の技術 — ★一番大きい判断

Rust の UI は Electron と違って Wayland の **layer-shell** が使える(画面端に場所を予約するバー・最前面のオーバーレイを、KWin スクリプトの工夫なしで作れる)。
付け替えやすさ・軽さ・layer-shell の 3 点で比べる。

| 案 | 付け替え(使用者が UI を変える) | 軽さ | layer-shell | 備考 |
|---|---|---|---|---|
| **A. Slint** | ◎ `.slint` ファイルを実行時に読み込める(slint-interpreter)。使用者はビルドせずに部品を差し替えられる | ◎ | △ 公式には無い(winit 経由。自前で足す必要あり) | 宣言的な UI 言語。部品 = `.slint` のコンポーネント |
| **B. iced** | △ Rust で書いてビルドし直す | ◎ | ○ `iced_layershell` がある | Elm 風。テーマは差し替えやすいが構造は固定 |
| **C. GTK4(gtk4-rs + gtk4-layer-shell)** | ○ CSS で見た目、`.ui`(XML)で構造を差し替えられる | ○ | ◎ 公式に近い | KDE 上で GTK になる |
| **D. Web(wry = WebKitGTK)で HTML の UI** | ◎ HTML/CSS/JS。今の `src/` の見た目を持っていける | △ | ○ GTK3 の layer-shell と組める | 中身は Rust だが UI は今と同じ作り方 |
| E. GPUI(以前の Rust 版) | △ | ◎ | △ | Zed 向けで、外から部品を足す仕組みは無い |

- おすすめ: **A. Slint**。「UI を抽象的に記述して付け替える」に一番素直に合う。部品の約束(判断 4)を Slint のコンポーネントの入出力(property / callback)として書けば、使用者は `.slint` を 1 つ置き換えるだけで部品を変えられる
  - 弱み: layer-shell を自前で足す必要がある。最初は今と同じ KWin スクリプトの疑似全画面で動かし、後で layer-shell に移す
- 次点: **D**。今の UI 資産をそのまま使えて移行は一番速いが、「ミニマル」から遠く、Webビューを 2 つ抱えることになる(Chromium と WebKitGTK)

### GPUI と Slint(候補はこの 2 つに絞った)

| | GPUI | Slint |
|---|---|---|
| 書き味 | Rust だけで書く。状態と描画が近く、速い UI(Zed)の実績 | UI は `.slint` 言語、処理は Rust。境目がはっきりする |
| 使用者の付け替え | 部品を変えるにはビルドし直す。外から足す仕組みは自前(別プロセスの UI か WASM) | `.slint` を実行時に読める。**ビルドなしで部品を差し替えられる** |
| 見た目だけの変更 | テーマ(色・字)を JSON で読む形なら容易 | 同じく容易 |
| API の安定 | Zed と一緒に変わる。資料が少ない | 1.x で安定。資料が多い |
| Linux / Wayland | 対応済み | 対応済み(winit) |

どちらでも成り立つようにする工夫: **判断 1 でコアと UI を分けたので、段階 1〜3 は UI の技術に依らない**。
段階 4 の前に、ナビ(スペースとブックマーク)の部品だけを両方で作って比べ、そこで決める。

- 「使用者がビルドせずに付け替える」を一番に置くなら Slint
- 「自分で書いて気持ちいい・速い」を一番に置くなら GPUI。その場合、付け替えは「UI の約束を別プロセスの UI にも出す(Unix ソケット)」で担保する(GPUI の既定 UI を丸ごと別のものにできる。部品単位の差し替えは弱くなる)

## 判断 3: ブラウザ — Chromium を切り離して「Web ペイン」として取り込む

今の Electron 版は Web を WebContentsView で自前で描いていて、合わないサイトだけ Chromium へ逃がしている(`behavior.chromiumSites`、`appembed.js` の `--app=` 窓)。
これを逆にして、**Web は全部 Chromium**、PRELUDE は Web エンジンを持たない。

取り込みの形(=「特別な形式」):

1. **Chromium は PRELUDE 専用のプロファイルで 1 つだけ起動** し、PRELUDE が子プロセスとして持つ
   (snap 版は今と同じく `~/snap/chromium/common/prelude-profile`)
2. 制御は **CDP(Chrome DevTools Protocol)を `--remote-debugging-pipe` で**。ポートを開けないので、他のプロセスから操作されない
3. **Web ペイン 1 つ = Chromium のアプリ窓 1 つ**(アドレスバー・タブバーなし)。CDP の `Target.createTarget { newWindow: true }` で作る
4. 窓は今のアプリの取り込みと同じく **KWin スクリプトでペインに重ねる**。どの Wayland 窓がどのペインかは、作った直後に CDP でページのタイトルに一時的な印を付けて KWin 側で見分ける
5. URL・タイトル・戻る/進む・読み込み中・ファビコンは CDP のイベントで受け、**アドレスバーや戻るボタンは PRELUDE の UI 側** に置く(Chromium の UI は見せない)
6. ダウンロード・権限の確認・拡張機能・パスワードは **Chromium に任せる**(今 `main.js` にある処理は消える)

**決めること 3-a: Chromium の窓の作り方**
- おすすめ: 上の 「1 つの Chromium + CDP でアプリ窓」
- 案: ペインごとに `chromium --app=URL` を別々に起動(今の方式。単純だが、URL やタイトルを PRELUDE が知れない)

**決めること 3-b: Chromium が無い PC**
- おすすめ: 起動時に `chromium` / `google-chrome` を探し、無ければ Web ペインは「Chromium を入れてください」の表示にする(Firefox などは対象外)

## 判断 4: UI の部品を抽象的に記述する

部品は「**何を表示し、何を送るか**」だけを約束として決め、見た目と並べ方は決めない。

| 部品(役割) | 受け取る状態 | 送るコマンド |
|---|---|---|
| `bar` | 時計・トレイ・状態・今のスペース | ランチャーを開く、クイック設定を開く |
| `nav` | スペースの一覧、ブックマーク(.prelude)の木 | スペース切替、ブックマークを開く/作る/動かす |
| `tabs` | タブの一覧・今のタブ | 切替・閉じる・並べ替え |
| `pane-frame` | ペインの種類・タイトル・URL など | 分割・閉じる・移動・URL を開く |
| `files` | フォルダの中身・選択・並べ方 | 開く・コピー・削除・名前変更… |
| `launcher` / `notifications` / `osd` / `quick` | それぞれの状態 | それぞれの操作 |

- **ペインの中身(Web・アプリ・コンソール)は取り込んだ窓** なので UI の部品ではない。UI はペインの「枠」と「場所」だけを持つ
- 使用者の UI は `~/.config/prelude/ui/<名前>/` に置く。中に `ui.toml`(どの部品をどこに置くか)と部品の実装(Slint なら `.slint`)。足りない部品は既定のものを使う
- 設定画面のスキーマ(今の `config.js`)も部品と同じく、コアが「設定の項目」を出し、UI が表示する

**決めること 4-a: 付け替えの単位**
- おすすめ: **部品ごと**(ナビだけ自作、ほかは既定、ができる)+ 並べ方は `ui.toml`
- 案: UI 全体を丸ごと(単純だが、少し変えたいだけでも全部書くことになる)

## 判断 5: `.prelude` = スペース 1 つ(決定)

### 考え方
- **保存先を決めるのは「プロセス(何をしているか)」** で、「プロセッサ(どのアプリか)」でも「ファイルがどこにあるか」でもない
- **スペース = 1 つのプロセス**。ホームからコマンドで切り替え、切り替えると今のタブは全部閉じ、切り替え先のブックマークを読み込む
- だから `paths` は **スペースだけが持つ**(ブックマーク・タブ・フォルダには持たせない)

退けた案と理由:
- ブックマーク(タブの配置)ごとに paths → アプリの並びに付くので、プロセッサ寄りになる
- 作業するフォルダの中に `.prelude/` を置く → 結局そのフォルダまでたどる手間が残る

### 形: 1 スペース = 1 ファイル(TOML)

```
~/スペース/
├── 論文執筆.prelude
├── 家計.prelude
└── PRELUDE開発.prelude
```

```toml
name = "論文執筆"

[paths]                     # この作業のフォルダ。項目は自由に増やせる
open     = "~/Dropbox/文献"  # アプリの「開く」ダイアログの最初のフォルダ
save     = "~/研究/論文/原稿" # アプリの「保存」ダイアログの最初のフォルダ
terminal = "~/研究/論文"      # コンソール・起動するアプリの作業フォルダ
files    = "~/研究/論文"      # ファイラの最初のフォルダ

[[bookmark]]
title  = "執筆"
layout = { ... }            # タブの配置(今の .prelude の root と同じ形)

[[bookmark]]
title = "文献を探す"
url   = "https://scholar.google.com"
```

### 決めごと(肥大化と責任の混ざりを防ぐ)
- **ファイルには使用者が決めたことだけ** を書く(paths とブックマーク)。前回開いていたタブなど PRELUDE が勝手に変えるものは `~/.local/state/prelude/` に置く
- 区切り(`[paths]`・`[[bookmark]]`)ごとに読む側が決まっている。読む側は自分の区切りだけを読み、**知らない項目は無視して残す**(書き戻しても消さない)
- `[paths]` の項目は自由。読む側(ダイアログのポータル・コンソール・ファイラ・ダウンロード・将来のプラグイン)は、知っている名前だけを使う。無い項目は `files` → ホームの順
- パスは `~/…` で書ける
- ブックマーク 1 つを人に渡すときは「書き出す」で、ブックマーク 1 つだけのスペースのファイルにする
- 人からもらったファイルの起動コマンドは、今と同じく確かめてから実行する

### 判断 5-a: アプリのダイアログ(決定)
- xdg-desktop-portal の FileChooser のバックエンドを PRELUDE(コア)が実装する。アプリの「開く」「保存」のダイアログが PRELUDE のファイラになり、最初のフォルダは今のスペースの `paths.open` / `paths.save`。`portals.conf` で KDE のものと置き換え、外せば KDE のダイアログに戻る

### 影響
- PR #66(スペース = フォルダ、ブックマーク = 中のファイル)と PR #71(paths をブックマークに付ける)は、この形で作り直す
- 0.11 までの JSON の `.prelude`(ブックマーク 1 つ)は、読み込んでスペースへ取り込む

### 未決
- スペースの中でブックマークをフォルダ分けするか(PR #66 のサブフォルダに当たるもの)
- 1 つのプロセスの中で、保存先を条件(アプリ・拡張子)で振り分けるか。今は「振り分けない。ダイアログで paths の項目から選び直す」を仮の答えとする
