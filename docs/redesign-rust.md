# PRELUDE 再設計: Rust への移行(設計判断の記録)

状態: **設計の論点は一通り決まった**(判断 15 まで。まだ決めていないものは無い)。決まったもの: 1-a(同じリポジトリ)、1-b(コアと UI は別プロセス、ペインの場所は UI)、3-a・3-c(Chromium 1 つ + CDP、タブは PRELUDE が戻す、プロファイル 1 つ)、5(スペース = フォルダ、`.prelude` = ブックマーク 1 つで paths を持つ、スペースは既定の paths)、5-a(ポータルを実装)、2(UI の技術。判断 11 で GPUI に置き換え)、4-a(部品ごとに付け替え・3 つの深さ・約束に版)、7(ペインの種類はレシピ → GPUI の部品 → プラグインの 3 段階)、8(試す間は同じデータ、GitHub でビルドして配る)、9(乗る先の OS は NixOS)、**10(UI はコマンドとランチャーだけ。サイドバーは GPUI で外付け、ウィジェットは rice。判断 1-b・2・4 の一部を置き換える)**、**11(UI はすべて GPUI、ランチャーは GPUI の自前で最初は fuzzel、コンポジタは SwayFX に決定)**、**12(残りの決めごと: Web ペインはアプリ窓、ダイアログの選ぶ画面はファイラの枠、PRELUDE を通さない窓の扱い、移行後は KDE を外す、トレイトに版を付けない、タブ = 作業領域)**、~~13(フィールドのカードはファイラに包含する)~~(判断 14 で取り消し)、**14(ファイラを PRELUDE から外す。既定は yazi。フィールド表示はやめる。ペインの `path` は汎用の欄で「開き始める場所」、ダイアログの選ぶ画面も yazi)**、**15(PRELUDE は OS の役割を持たない。本体はコア・コマンド・ランチャー、窓・ダイアログ・サイドバーは環境ごとの「つなぎ」、外回り・OS の設定・セッション・更新は環境に任せる。判断 9 は作者の環境の記録に格下げ、判断 12 の「KDE を外す」は取り消し)**。
判断 2(UI の技術)は Slint に決めたが、**判断 11 で GPUI に置き換えた**。

## 0. 目的

もっと使いやすく、ミニマルで、拡張しやすいものにする。そのために次の 4 つを変える。

1. 本体を Electron(JS)から **Rust** に移す
2. ブラウザを PRELUDE から切り離す。Web は **Chromium そのもの** にして、PRELUDE はそれを決まった形で取り込む
3. サイドバー・ファイラなどの UI の部品を **抽象的に記述** する。見た目と実装は使用者が付け替えられる
4. `.prelude`(ブックマーク)に **パス**(開く・保存・コンソール…)を持たせる。スペース(= 1 つのプロセス)は既定のパスを持つ

KDE に任せる範囲(KWin・ロック画面・電源など)は今と同じ([shell-design.md](shell-design.md) の 1 章)。

## 判断 1: 全体の構成 — 「コア」と「UI」を分ける

```
┌─ prelude-core(Rust・常駐) ───────────────────────────┐
│ 状態: スペース / タブ / 分割 / ペイン / .prelude          │
│ OS:   KWin(窓の取り込み・配置)、Chromium の制御、       │
│       ファイル操作・監視、D-Bus(通知・トレイ・OSD・音量)│
│ 公開: コマンドとイベント(下の「UI の約束」)            │
└───────────────▲───────────────────────────────────────┘
                │ UI の約束(Unix ソケット。コマンドとイベント)
┌───────────────┴───────────────────────────────────────┐
│ UI(付け替えられる) 既定の UI = 部品の組み合わせ       │
│ バー / ナビ(スペース・ブックマーク) / タブ / ペインの枠 │
│ ファイラ / ランチャー / 通知 / OSD / クイック設定        │
└───────────────────────────────────────────────────────┘
```

- コアは画面を持たない。**状態の持ち主** で、UI は状態を表示してコマンドを送るだけ
- 今の `fileops.js` の冒頭に書いた「OS に近い部分は将来 Rust に置き換える」をそのまま広げた形

### 判断 1-b: コアと UI の境目(決定。②・③ は判断 10 で見直し)

> **判断 12 で見直した。** PRELUDE の窓が無くなる(判断 10)ので、② ペインの場所は **コンポジタが並べる**(分割の構造と比率を覚えるのは今までどおりコア)。③ どこでも効くキーは **コンポジタが受けて `prelude` コマンドを呼ぶ**(割り当ての断片は PRELUDE の NixOS モジュールが出す)。

| | 決めたこと | 理由 |
|---|---|---|
| ① プログラム | **コアと UI は別のプロセス**。間は Unix ソケット(コマンドとイベント) | UI が落ちてもタブ・取り込んだアプリは残り、UI だけ立ち上げ直せば戻る。UI を PRELUDE ごと止めずに付け替えられる。`prelude` コマンドや外部のスクリプトも同じソケットを使う |
| ② ペインの場所 | **UI が決めて、コアに知らせる**。分割の構造(どこで左右・上下に分けたか、比率)はコアが覚える。何ピクセルに置くかは UI | 並べ方を UI ごとに自由にできる(「見せ方は自由」)。今の Electron 版と同じ流れ(UI → コア → KWin) |
| ③ ショートカット | **どこでも効くキー**(スペース切替・ランチャー・タブ移動)は **コア**。**部品の中だけのキー**(ファイラの矢印・名前の変更)は **部品**。割り当てはどちらも 1 つの設定ファイル | UI を付け替えても同じキーで動く |
| ④ 覚えること | **残すものはコア**(スペース・タブ・分割・開いているブックマーク)。**UI は今の見た目だけ**(スクロール位置・選んでいる行など。付け替えたら消えてよいもの) | UI が落ちても・付け替えても作業が消えない |

- UI がまだ場所を知らせていないペイン(UI の起動中・立ち上げ直し中)の窓は、コアが隠しておく

**決めること 1-a: 同じリポジトリか、新しいリポジトリか**
- おすすめ: **このリポジトリに Cargo のワークスペース(`crates/`)を足す**。Electron 版は Rust 版が日常の用途を満たすまでリリースとして残し、満たした時点で消す。`.prelude` の形式とテストを両方で確かめられる
- 案: 新しいリポジトリ(`PRELUDE` の名前に戻す、など)

## 判断 2: UI の技術 — Slint(判断 11 で GPUI に置き換え)

> **判断 11 で置き換えた。** PRELUDE の UI(サイドバー・ランチャー・ファイラ)はすべて GPUI で作り、Slint は使わない。以下は Slint に決めたときの記録。

**Slint に決めた。** 決め手は「部品の見た目と並べ方を、ビルドなしで付け替えられる」こと(判断 4 の深さ 2)。
性能はどちらも Electron より大幅に軽く、差は決め手にならない。この PC(Iris Xe・メモリ 7.4GB で余裕が少ない)では、メモリの少なさと、GPU が不調でもソフトウェアで描けて画面が必ず出ることが Slint の利点。
GPUI を選ぶと「ビルドなしの付け替え」の道が閉じるので、付け替えの深さがまだ決まっていない今は、道を残す方を選んだ。

- 既定の部品は **ビルド時に組み込む**(速さは普通の Rust の UI と同じ)。使用者が置き換えた部品だけを **実行時に読み込む**(slint-interpreter)
- Slint は使ったことがないので、段階 4 より前に **小さな試作で次を確かめる**:
  - 日本語入力(fcitx5 / ibus。Wayland の text-input)・日本語のフォント
  - 長い一覧(ファイル 1 万件)の速さとメモリ
  - 実行時に `.slint` を読み込んで部品を差し替える流れ
  - layer-shell(バー・オーバーレイ)をどう足すか。だめなら今の KWin スクリプトの疑似全画面で動かす

以下は決める前の比較(記録として残す)。


Rust の UI は Electron と違って Wayland の **layer-shell** が使える(画面端に場所を予約するバー・最前面のオーバーレイを、KWin スクリプトの工夫なしで作れる)。
付け替えやすさ・軽さ・layer-shell の 3 点で比べる。

| 案 | 付け替え(使用者が UI を変える) | 軽さ | layer-shell | 備考 |
|---|---|---|---|---|
| **A. Slint** | ◎ `.slint` ファイルを実行時に読み込める(slint-interpreter)。使用者はビルドせずに部品を差し替えられる | ◎ | △ 公式には無い(winit 経由。自前で足す必要あり) | 宣言的な UI 言語。部品 = `.slint` のコンポーネント |
| **B. iced** | △ Rust で書いてビルドし直す | ◎ | ○ `iced_layershell` がある | Elm 風。テーマは差し替えやすいが構造は固定 |
| **C. GTK4(gtk4-rs + gtk4-layer-shell)** | ○ CSS で見た目、`.ui`(XML)で構造を差し替えられる | ○ | ◎ 公式に近い | KDE 上で GTK になる |
| **D. Web(wry = WebKitGTK)で HTML の UI** | ◎ HTML/CSS/JS。今の `src/` の見た目を持っていける | △ | ○ GTK3 の layer-shell と組める | 中身は Rust だが UI は今と同じ作り方 |
| E. GPUI(以前の Rust 版) | △ | ◎ | △ | Zed 向けで、外から部品を足す仕組みは無い |

- おすすめ: **A. Slint**。「UI を抽象的に記述して付け替える」に一番素直に合う。部品の約束(判断 4)を Slint のコンポーネントの入出力(property / callback)として書けば、使用者は `.slint` を 1 つ置き換えるだけで部品を変えられる
  - 弱み: layer-shell を自前で足す必要がある。最初は今と同じ KWin スクリプトの疑似全画面で動かし、後で layer-shell に移す
- 次点: **D**。今の UI 資産をそのまま使えて移行は一番速いが、「ミニマル」から遠く、Webビューを 2 つ抱えることになる(Chromium と WebKitGTK)

### GPUI と Slint(候補はこの 2 つに絞った)

| | GPUI | Slint |
|---|---|---|
| 書き味 | Rust だけで書く。状態と描画が近く、速い UI(Zed)の実績 | UI は `.slint` 言語、処理は Rust。境目がはっきりする |
| 使用者の付け替え | 部品を変えるにはビルドし直す。外から足す仕組みは自前(別プロセスの UI か WASM) | `.slint` を実行時に読める。**ビルドなしで部品を差し替えられる** |
| 見た目だけの変更 | テーマ(色・字)を JSON で読む形なら容易 | 同じく容易 |
| API の安定 | Zed と一緒に変わる。資料が少ない | 1.x で安定。資料が多い |
| Linux / Wayland | 対応済み | 対応済み(winit) |

どちらでも成り立つようにする工夫: **判断 1 でコアと UI を分けたので、段階 1〜3 は UI の技術に依らない**。
段階 4 の前に、ナビ(スペースとブックマーク)の部品だけを両方で作って比べ、そこで決める。

- 「使用者がビルドせずに付け替える」を一番に置くなら Slint
- 「自分で書いて気持ちいい・速い」を一番に置くなら GPUI。その場合、付け替えは「UI の約束を別プロセスの UI にも出す(Unix ソケット)」で担保する(GPUI の既定 UI を丸ごと別のものにできる。部品単位の差し替えは弱くなる)

## 判断 3: ブラウザ — Chromium を切り離して「Web ペイン」として取り込む

今の Electron 版は Web を WebContentsView で自前で描いていて、合わないサイトだけ Chromium へ逃がしている(`behavior.chromiumSites`、`appembed.js` の `--app=` 窓)。
これを逆にして、**Web は全部 Chromium**、PRELUDE は Web エンジンを持たない。

取り込みの形(=「特別な形式」):

1. **Chromium は PRELUDE 専用のプロファイルで 1 つだけ起動** し、PRELUDE が子プロセスとして持つ
   (snap 版は今と同じく `~/snap/chromium/common/prelude-profile`)
2. 制御は **CDP(Chrome DevTools Protocol)を `--remote-debugging-pipe` で**。ポートを開けないので、他のプロセスから操作されない
3. **Web ペイン 1 つ = Chromium のアプリ窓 1 つ**(アドレスバー・タブバーなし)。CDP の `Target.createTarget { newWindow: true }` で作る
4. 窓は今のアプリの取り込みと同じく **KWin スクリプトでペインに重ねる**。どの Wayland 窓がどのペインかは、作った直後に CDP でページのタイトルに一時的な印を付けて KWin 側で見分ける
5. URL・タイトル・戻る/進む・読み込み中・ファビコンは CDP のイベントで受け、**アドレスバーや戻るボタンは PRELUDE の UI 側** に置く(Chromium の UI は見せない)
   - **判断 12 で見直した**: PRELUDE の窓が無いので、アドレスバーは置かない。URL・タイトルはサイドバーに出し、URL を書き換えるのは「今の URL が入った状態のランチャー」。戻る・進むは Chromium のキー(Alt+←/→)
6. 権限の確認・拡張機能・パスワード・ログインは **Chromium に任せる**(今 `main.js` にある処理は消える)。ダウンロードは下の 3-c

**判断 3-a: Chromium の窓の作り方(決定)**
- 上の 「1 つの Chromium + CDP でアプリ窓」
- 案: ペインごとに `chromium --app=URL` を別々に起動(今の方式。単純だが、URL やタイトルを PRELUDE が知れない)

**Web のペインと CDP(2026-11-06 に変更)**
CDP をやめて、小さな拡張機能でつなぐ。`--remote-debugging-pipe` で起動すると `navigator.webdriver` が `true` になり(普通の起動は `false`。同じ Chromium 156 で比べた)、Google のログインが「安全でないブラウザ」として拒まれる。拡張機能だけで起動すると、Google のパスワードと 2 段階の確認を経て Notion へログインできた。

- 拡張機能(`crates/prelude-core/extension/`)はコアに埋め込み、起動のときに書き出す。事実を知らせて頼まれたことをするだけで、判断は `web.rs` の `decide` がする
- つなぎ方は native messaging。Chromium が `prelude-core --web-host` を起動し、これがコアの Unix ソケット(`core.web`)へつなぐ。宣言は `<プロファイル>/NativeMessagingHosts/` に置く。id は `manifest.json` の `key` で固定する
- 読み込みは `--load-extension`(Google 版の Chrome では外された引数なので、Chromium を使う)
- タブ付きの窓(`normal`)に出た http(s) のページは閉じて PRELUDE のタブにする。`popup` はそのまま(ログイン)。Chromium のタブを PRELUDE の側で管理する
- ダウンロードの保存先は絶対パスで頼めないので、終わってからコアが移す
- Chromium は窓が無くなると終わる。次の Web のペインで起動し直す

下の CDP の記述は、窓の作り方(`--app` と印のページ)を除いて古い。

**Web のペインの作り方(段階 3-b で分かったこと。上の 3〜4 を具体的にしたもの)**
- CDP の `Target.createTarget { newWindow: true }` で作る窓は、タブ・アドレスバーのある普通の窓になる(アプリの窓にする引数が無い)。そこで、動いている Chromium に同じプロファイルで `--app=<URL>` を頼む(頼んだプロセスはすぐ終わり、CDP の側に新しいページとして現れる)
- `--app=` は `data:` や `about:blank` では窓にならない。そこで題名に印を出すだけのページ(`prelude-pane.html`。snap 版が読める `~/snap/chromium/common` に置く)を `file:///…/prelude-pane.html#<コアの印>:<ペイン>` で開く。題名が `PRELUDE-PANE:<コアの印>:<ペイン>` になるので、KWin スクリプトはその窓を取り込み、取り込んだら CDP で本当の URL へ移す
- snap 版の Chromium には終了の合図(シグナル)を送れない(AppArmor)。終わらせるときは、窓を閉じてから CDP の通信の口を閉じる。snap 版は普通に閉じてもプロファイルに「落ちた」と記録されるので(CDP を使わなくても同じ。Electron 版の Chromium の窓も同じ)、起動するときに `--hide-crash-restore-bubble` を付ける
- 新しいタブで開くリンク(noopener)と、ログインなどの小さな窓(opener のあるもの)は、CDP の `canAccessOpener` で見分ける
- Chromium は `PATH` から探す(`xdg.rs`。判断 9)。snap 版かどうかは実体のパスで見分け、snap 版ならプロファイルと印のページを `~/snap/chromium/common` に置く
- 判断 12 に合わせて: ログインなどの小さな窓(opener のあるもの)は「親のある窓」として浮かせたまま。戻る・進むはふだんは Chromium のキー(Alt+←/→)で、`web.go` は同じことをコマンドからするためのもの(判断 10 の「コマンドで完結する」)

**判断 3-b: Chromium が無い PC(判断 12 で決定)**
- NixOS のモジュールが Chromium を入れるので、無いときの扱いは作らない。Chromium は `PATH` から探す(`sys/xdg.js`・`xdg.rs`)

**判断 3-c: Chromium との分担(決定)**

| | 決めたこと |
|---|---|
| 立ち上げ直し | **PRELUDE(コア)が戻す**。コアがペインの URL を覚えていて、Chromium に開き直させる。Chromium 自身の「前回のページを開く」は切る。ページ内の戻る履歴・スクロール位置・入力途中のフォームは戻らない(今と同じ) |
| 新しい窓 | 普通のリンク(新しいタブで開く)は **PRELUDE の新しいタブか分割**(今の設定「リンクの開き方」)。ログイン用などの小さなポップアップ(`window.open` で大きさ指定のあるもの)は **取り込まず、小さな窓のまま前に出す** |
| ダウンロード | 保存先は **ダウンロードを始めたタブのブックマークの `paths`**(`download` → `save` → スペースの既定…)。進み具合と保存先の変更は PRELUDE の UI に出す(今と同じ) |
| プロファイル | **1 つだけ**。どのスペースでも同じログイン状態。スペースごとに分ける(`space.toml` の `profile`)は、要るようになったら足す |

## 判断 4: UI の部品を抽象的に記述する(判断 10 で大きく変わった)

> **判断 10 で、付け替えは 2 段になった。** ① **部品**: サイドバーなどのプログラムの中の部品を、トレイトで差し替える(ビルドが要る。`.slint` を実行時に読む形はやめた)。② **プログラム**: ソケットの約束があるので、サイドバー・ファイラ・ランチャーの見た目・ウィジェットを丸ごと別のプログラムにできる。部品の表(受け取る状態・送るコマンド)は、どちらの段でも約束として生きている。

部品は「**何を表示し、何を送るか**」だけを約束として決め、見た目と並べ方は決めない。

| 部品(役割) | 受け取る状態 | 送るコマンド |
|---|---|---|
| `bar` | 時計・トレイ・状態・今のスペース | ランチャーを開く、クイック設定を開く |
| `nav` | スペースの一覧、ブックマーク(.prelude)の木 | スペース切替、ブックマークを開く/作る/動かす |
| `tabs` | タブの一覧・今のタブ | 切替・閉じる・並べ替え |
| `pane-frame` | ペインの種類・タイトル・URL など | 分割・閉じる・移動・URL を開く |
| `files` | フォルダの中身・選択・並べ方 | 開く・コピー・削除・名前変更… |
| `launcher` / `notifications` / `osd` / `quick` | それぞれの状態 | それぞれの操作 |

- **ペインの中身(Web・アプリ・コンソール)は取り込んだ窓** なので UI の部品ではない。UI はペインの「枠」と「場所」だけを持つ
- 使用者の UI は `~/.config/prelude/ui/<名前>/` に置く。中に `ui.toml`(どの部品をどこに置くか)と部品の実装(Slint なら `.slint`)。足りない部品は既定のものを使う
- 設定画面のスキーマ(今の `config.js`)も部品と同じく、コアが「設定の項目」を出し、UI が表示する

- 同じデータを受け取る部品はいくつあってもよい。例: 今の「フォルダ」と「フィールド」は、どちらも「フォルダの中身」を受け取る `files` の部品

**判断 4-a: 付け替え(決定)**
- **部品ごと** に付け替えられる(サイドバーだけ自作、ほかは既定、ができる)。どの場所にどの部品を置くかは `ui.toml`
- 付け替えには 3 つの深さがある

  | 深さ | 変えるもの | どうやって |
  |---|---|---|
  | 1. テーマ | 色・字・余白 | `theme.toml`。全部の部品が同じ値を使う |
  | 2. 見た目と並べ方 | 部品の形 | `.slint` を置き換える(ビルドなし) |
  | 3. 動き | 部品の振る舞い | Rust で書いてビルド |

- **約束には版の番号を付ける**。コアが新しくなっても、古い約束で作った部品が動き続けるようにする
- 部品の約束(受け取るもの・頼めること)は、Slint のコンポーネントの入出力(property と callback)としてそのまま書く。これが使用者が `.slint` を書くときの説明書になる

## 判断 5: スペースと `.prelude`(決定)

### 考え方
- **保存先を決めるのは「プロセス(何をしているか)」** で、「プロセッサ(どのアプリか)」ではない
- **スペース = 1 つのプロセス** = フォルダ 1 つ。ホームからコマンドで切り替え、切り替えると今のタブは全部閉じ、切り替え先のブックマークを読み込む
- **`.prelude` = ブックマーク 1 つ**。スペースのフォルダの中にたくさん置く。ブックマークのフォルダは、スペースの中の本物のフォルダ
- **`paths` はブックマークが持つ**。スペースは、ブックマークに書いていないときの既定の `paths` を持つ

### 形

```
~/スペース/
└── 論文執筆/                 ← スペース(フォルダ) = 1 つのプロセス
    ├── space.toml            ← スペースの設定: 既定の paths
    ├── 本文.prelude           ← ブックマーク 1 つ
    ├── 文献を探す.prelude
    └── 執筆/                  ← ブックマークのフォルダ(本物のフォルダ)
        └── 図.prelude
```

```toml
# space.toml — ブックマークに書いていない項目の既定
[paths]
files    = "~/研究/論文"
terminal = "~/研究/論文"
```

```toml
# 本文.prelude — ブックマーク 1 つ
title = "本文"

[paths]                       # 項目は自由に増やせる
open     = "~/Dropbox/文献"    # アプリの「開く」ダイアログの最初のフォルダ
save     = "~/研究/論文/原稿"   # アプリの「保存」ダイアログの最初のフォルダ
terminal = "~/研究/論文/src"    # コンソール・起動するアプリの作業フォルダ
files    = "~/研究/論文"        # ファイラの最初のフォルダ

[layout]                      # タブの配置(今の .prelude の root と同じ形)
# ...
```

### どの paths を使うか
- **今開いているブックマーク**(表示しているタブが開いたブックマーク)の `paths` を使う。アプリのダイアログ・コンソール・ファイラ・ダウンロードのどれも同じ
- 項目ごとに、ブックマーク → スペース(`space.toml`)→ `files` → ホーム の順で決める
- 今のタブがブックマークから開いたものでなければ(新しいタブなど)、スペースの既定から決める
- パスは `~/…` と、ファイルがあるフォルダからの相対パスで書ける

### 決めごと
- **ファイルには使用者が決めたことだけ** を書く。前回開いていたタブ・折りたたみの開閉など PRELUDE が変えるものは `~/.local/state/prelude/` に置く
- `[paths]` の項目は自由。読む側(ダイアログのポータル・コンソール・ファイラ・ダウンロード・将来のプラグイン)は知っている名前だけを使う。**知らない項目は無視して残す**(書き戻しても消さない)
- **UI ごとの区画**: UI の部品が自分だけの情報(フィールドのカードの位置、グループの色、使用者が決めた並び順など)を残すときは、`.prelude` / `space.toml` の `[ui.<部品名>]` に書く。部品は自分の区画だけを読み書きする。見せ方は部品が自由に決める(判断 4)
- 人からもらった `.prelude` の起動コマンドは、今と同じく確かめてから実行する

### 判断 5-a: アプリのダイアログ(決定)
- xdg-desktop-portal の FileChooser のバックエンドを PRELUDE(コア)が実装する。アプリの「開く」「保存」のダイアログが PRELUDE のファイラになり、最初のフォルダは今開いているブックマークの `paths.open` / `paths.save`。`portals.conf` で KDE のものと置き換え、外せば KDE のダイアログに戻る
- **判断 12 で見直した**: コアは最初のフォルダを決めるだけにし、選ぶ画面はファイラの枠(判断 10)に選んだもの(GPUI のファイラ・yazi など)を使う

### 影響
- PR #66(スペース = フォルダ)の形はそのまま使える。`space.toml` を足す
- PR #71(ブックマークの paths)の考え方もそのまま。スペースの既定と「今開いているブックマーク」の決め方を足す
- 0.11 までの JSON の `.prelude` も読めるようにする

### 仮に決めたこと(あとで変えてよい)
- `.prelude` も TOML にする(`space.toml` と揃える)
- `space.toml` は隠しファイルにしない
- `tags`(フォルダをまたぐ目印)は後回し

## 判断 7: ペインの種類を増やす(決定)

今のペインは 2 つの仲間に分かれる。

| 仲間 | ペイン | 中身を描くのは |
|---|---|---|
| A. 窓を取り込む | Web(Chromium)・アプリ・コンソール | ほかのプログラム。PRELUDE は場所を決めるだけ |
| B. PRELUDE が描く | フォルダ・フィールド・ホーム・設定 | UI の部品(GPUI。判断 11) |

増やし方は 3 段階。**3 つとも設計に入れ、作るのは段階 1 から。**

1. **レシピ**(仲間 A を設定ファイルだけで増やす)

   ```toml
   # ~/.config/prelude/panes/console.toml
   name = "コンソール"
   run  = "konsole --workdir {paths.terminal}"   # {…} は今のブックマークの paths などに置き換わる
   ```

   - コンソールも特別扱いをやめ、レシピの 1 つにする
   - `.prelude` には `type = "console"` のように **種類の名前だけ** を書く。コマンドは自分の設定にしか無いので、人からもらったファイルが勝手なコマンドを実行できない
2. **GPUI の部品**(仲間 B を、コアが持っているデータの新しい見せ方として増やす)。部品のトレイト(ファイラなら `FilerView`)を満たす部品として足す(ビルドが要る。判断 11)。例: 写真を大きく並べるペイン
3. **プラグイン**(コアが持っていないデータを持ち込む。カレンダー・タスクなど)
   - **別のプログラム** として作り、コアと同じソケットでつなぐ。「このデータを出す」「この操作を受ける」と名乗り出て、見た目は段階 2 と同じく GPUI の部品が描く
   - 言語は自由(Python でもよい)。プラグインが落ちても PRELUDE は落ちない
   - PRELUDE の中に組み込む方法(WASM・共有ライブラリ)は、複雑さと巻き込まれて落ちる危険から採らない
   - ソケットの約束が固まってから作る

- **知らない種類**(この PC にレシピ・部品・プラグインが無い)のペインは「この種類は入っていません」と表示し、**書かれていた中身はそのまま残す**(今のようにフォルダのペインに変えない)
- **起動コマンドを直接書くアプリのペイン** は残す。自分で作ったブックマークは今までどおり。人からもらったものは今と同じく、インストール済みのアプリと一致しないコマンドを確かめてから実行する

### ソケットの約束(版 1。段階 2 で作ったもの)

型は `crates/prelude-proto` が正。ここは見取り図。

- 場所: `$PRELUDE_CORE_SOCK` → `$XDG_RUNTIME_DIR/prelude/core.sock`。フォルダは 0700、ソケットは 0600
- 1 行 1 つの JSON(1 行は 1MB まで)。送る: `{"id": 1, "cmd": "tab.open", "args": {...}}`(`args` は省ける)。返る: `{"id": 1, "result": …}` か `{"id": 1, "error": {"code", "message"}}`
- 最初に `hello {protocol, name, subscribe}`。版が合わなければ `protocol` のエラー。`subscribe` すると、すぐに今の状態、その後は変わるたびに `{"event": "state", "data": State}`
- コマンド: `state.get`、`space.list / switch / create`、`bookmark.list / open`、`tab.open / close / activate / move`、`pane.split / close / update / focus / place`、`split.ratio`、`paths.get`
- 配置は `.prelude` の `[layout]` と同じ形で、ペインに `id` が付く。タブは `{"id"}` か画面の番号 `{"num"}` で指し、省くと今のタブ
- エラーの種類: `bad_request`・`unknown_command`・`protocol`・`not_found`・`conflict`・`io`
- 版の決まり: コマンド・項目・イベントを **足すだけなら版は上げない**(受け取る側は知らないものを無視する)。意味を変える・消すときは版を上げ、コアは古い版も話し続ける(`SUPPORTED`)

ランチャーの候補で足したもの: `item.list`(→ `Item { key, kind, label, detail, score }`)、`item.open { key, allow }`。key は `tab:<id>`・`bookmark:<パス>`・`app:<.desktop の id>`・`space:<名前>`。開いたもの(`bookmark.open`・`space.switch` も)は点数に足す

段階 3-a で足したもの: `recipe.list`、`bookmark.open` の `allow` と返事の `held`(外した起動コマンド)、ペインの `window_title`・`stopped`。取り込みの D-Bus は `org.prelude.Core`(`/org/prelude/Core` の `Report`。KWin スクリプトが呼ぶ)

段階 3-b で足したもの: `web.go`、`download` のイベント

まだしていないこと: ブックマークのフォルダの監視、ショートカット、`prelude-core` を systemd で常駐させること、UI の窓より上に取り込んだ窓を出し直すこと(UI ができてから。今は最前面に置くだけ)

## 判断 9: 乗る先の OS — NixOS(判断 15 で作者の環境の記録に格下げ)

> **判断 15 で見直した。** PRELUDE は OS を前提にしない。以下は「作者の PC を NixOS にする」決めごととして残す。

PRELUDE が頼っているのは **KDE Plasma 6 + Wayland(KWin)** で、Ubuntu そのものではない。Ubuntu に固有なのは snap 版の Chromium の扱いと、SDDM の設定ファイルの名前くらいで、どれも得をしていない。
そこで、乗る先を PRELUDE の思想に照らして選び直し、**NixOS** にする。ディストリビューションを自分で作ることはしない(カーネル・ドライバ・KDE の保守まで持つことになる)。

### 思想と照らす

| 思想 | 出どころ | NixOS では |
|---|---|---|
| 任せられるものは任せる。PRELUDE は自分の層だけを持つ | shell-design.md 1章、判断 3 | KDE・Chromium・カーネルは nixpkgs が保守する。PRELUDE はモジュール 1 つ |
| ファイルには使用者が決めたことだけを書く。PRELUDE が変えるものは別に置く | 判断 5 | OS 全体を 1 つの設定で宣言する。`.prelude` と同じ考え方 |
| 落ちても・失敗しても戻れる | 判断 1-b、release.md | 前の世代へ戻せる(起動の画面でも選べる)。`release.sh switch` が OS ごとになる |
| 土台と付け替える部分を分ける | 判断 1・4 | 読み取り専用の `/nix/store` と、使用者の設定 |
| ミニマル | 判断 0・2 | 書いたものしか入らない |

比べた候補: Kubuntu(手で積み重ねる・snap・Plasma が遅れる)、Fedora KDE、Arch(戻せない)、Fedora Kinoite + bootc(思想にはよく合い、移行中の Electron 版も普通に動く。NixOS が合わなかったときの次の候補)。

### PRELUDE 側で変えること

| 今 | NixOS では |
|---|---|
| `/usr/bin/konsole`・`/snap/bin/chromium`・`/usr/share/icons`・`/bin/bash` などの決め打ち | `PATH` と `XDG_DATA_DIRS` から探す(`sys/xdg.js`・`crates/prelude-core/src/xdg.rs`)。**済** |
| npm の `electron`(`node_modules/electron/dist/electron`) | NixOS では動かない(普通のファイルの配置が無い)。nixpkgs の `electron`(版を合わせる)で `electron .`。ネイティブモジュールは無いので、ほかの依存はそのまま |
| `scripts/theme.sh`(sudo で SDDM・ロック画面のテーマを置く、`quiet splash`) | NixOS のモジュールに書く(SDDM のテーマ・`boot.kernelParams` など) |
| `systemd/prelude-shell*.service`、`scripts/shell-mode.sh` | モジュールの `systemd.user.services` |
| `release.sh` + `sys/update.js`(タグから作って切り替え・前の版に戻す) | flake の入力をタグに合わせて `nixos-rebuild switch`。戻すのは NixOS の世代 |
| 「Kubuntu に戻る」 | 「plasmashell に戻る」(中身は同じ) |
| 判断 8 の配布(GitHub Actions でビルドしてリリースに添付) | このリポジトリの `flake.nix` と NixOS のモジュール(`services.prelude.enable`)。ビルドの結果は Nix のキャッシュで配れる |

### 確かめること(NixOS を試すとき)

- nixpkgs の `electron` で今の Electron 版が動くか(版の違い)
- 日本語入力(`i18n.inputMethod` で fcitx5)、Iris Xe
- アプリの取り込み: NixOS では包まれたプログラムのプロセス名が `.konsole-wrapped` のようになる。`/proc` で窓の持ち主を見分ける所(`appembed.js`・`embed.rs`・`procs.rs`)が合うか
- KWin スクリプト・シェルモード・ロック画面と SDDM のテーマ
- `.desktop` の `Exec` が `/nix/store/…` の絶対パスになるアプリで、人からもらったブックマークの起動コマンドの確かめが働くか

### 移行の方針(2026-11-04)
PRELUDE の開発を止めても Ubuntu を使い続ける利点は薄いので、**試してから戻すのではなく、NixOS へ移る** つもりで進める。ただし Kubuntu はすぐ消さず、横に入れて確かめてから消す。
- `flake.nix` に開発環境、`nix/configuration.nix` に最小の OS の設定だけを書く。今の Kubuntu の中身は書き写さず、足りないものをその都度足す
- メモリの節約にはならない(この PC で使っているのはアプリで、減るのは Discover と snapd の 130MB ほど)。スワップの不足は zram で補う
- この PC では仮想マシンを使わない(メモリ 7.6GB に 3.5GB を割り当てて、OOM で落ちた)
- 2026-11-05: NixOS を `nvme0n1p3` に入れ、起動・ログイン・`nixos-rebuild` まで確かめた(Kubuntu は `nvme0n1p2` に残っている)。Claude のデスクトップアプリは公式の .deb を `nix/claude-desktop.nix` で包む(Kubuntu の上の Nix で起動を確認)。pCloud は nixpkgs にある。open-pdf-studio も公式の .deb を `nix/open-pdf-studio.nix` で包む(MCP は 9223 番で答える)。ペンタブレットのドライバ(xppenlinux)は入れない
- flake は `path:` で指さない(リポジトリ全体、ビルド結果の 16GB までストアにコピーされる)。`.#…` なら git の追跡分だけ
- nixos-26.05 の既定は rustc 1.95・electron 43 で、PRELUDE には古い。`flake.nix` で `rust-overlay` の配布済みの 1.98.1(GPUI の指定に合わせる)と `electron_44` を選ぶ
- Kubuntu の上の Nix で確かめた(`nix develop`。2026-11-04): コアとコマンドのテスト、`npm test`(47)、GPUI の 3 つのビルド(2 並列で 8 分半)が通り、ファイラは Nix の Mesa を `VK_DRIVER_FILES` で指定すると Iris Xe の Vulkan で動く。Electron 44 は PRELUDE の画面まで読み込む。Kubuntu の上では GL のドライバが見つからないエラーが出る(`/run/opengl-driver` が無いため。NixOS で確かめる)
- `nix-daemon` のビルドには `systemd-run` の上限が効かない。手元で Rust をコンパイルさせると OOM になるので、実行前に `nix build --dry-run` でビルドするものを見る
- `nix/hardware-configuration.nix` は入れる PC で作る。EFI 区画が 300MB なので、カーネルをルートの `/boot` に置く GRUB にする

### 順番

1. 今の Kubuntu のまま準備する: 決め打ちのパスを無くす(済)、この判断を書く(済)
2. NixOS を別の区画か USB に入れて、上の「確かめること」を試す。`flake.nix`(Electron 版・Rust 版のパッケージ、`nix develop`)はここで作る(NixOS の上で確かめないと動くか分からないため)
3. NixOS のモジュールを書き、シェルとして常用する。更新の仕組みを世代に置き換える
4. 移る。データ(`~/スペース`、Chromium のプロファイル)はホームごと持っていく。移る時期は段階 8(Electron 版を消す)に合わせるのが一番無理がない

## 判断 10: UI はコマンドとランチャーだけ。サイドバーは外付け、ウィジェットは rice(決定)

> **判断 15 で広げた。** ランチャーは本体に入れ、サイドバーは「つなぎ」、rice は「環境」として PRELUDE の外に置く。

rice(コンポジタと小さな部品を組み合わせて自分のデスクトップを作ること)と合わせて使う前提で、PRELUDE の UI を最小にする。
**PRELUDE の窓の中にペインを並べる形はやめる。** 窓を並べる・見た目を決めるのはコンポジタで、PRELUDE はスペース・ブックマーク・paths(何をしているか)を管理する。

### 形

| 層 | 中身 | 要るか |
|---|---|---|
| 0. コア + コマンド | `prelude-core` と `prelude` コマンド。タブの切り替えなど、ほぼ全部の機能がコマンドで完結する | 必須 |
| 1. ランチャー | コアが候補と点数(履歴)を出し、選んだものを開く | ほぼ必須 |
| 2. 外付けの UI | **サイドバー(GPUI)**。ほかにも PRELUDE にしか無い部品(フィールド表示など)を足すときは、別のプログラムにする | 好みで |
| 3. rice | コンポジタ・バー・通知・OSD・トレイ・ロック・壁紙など(ウィジェット類) | 好みで |

### 付け替えの 2 段
| 段 | 付け替えるもの | どうやって |
|---|---|---|
| 部品 | サイドバーなどの中の部品(タブの一覧・ブックマークの木など) | トレイトで差し替える。ビルドが要る |
| プログラム | サイドバー・ファイラ・ランチャーの見た目・ウィジェットを丸ごと | ソケットの約束(`prelude-proto`)だけでつながるので、別のプログラムに替えられる |

### 決めごと
- **サイドバーにだけ許された操作を作らない。** サイドバーもコマンドと同じソケットの約束(`prelude-proto`)を使う。これで「コマンドで完結する」が崩れず、ほかの人が別のサイドバーを作ることもできる
- **サイドバーは GPUI**(判断 11 で、PRELUDE の UI はすべて GPUI にした)。サイドバーは PRELUDE と強く結び付いていて、コアの型・トレイトをそのまま使える方がよい(`prelude-proto` の上の型付きのクライアント)。頻繁に付け替えるものではないので、ビルドが要ることは弱みにならず、速さと書き味を取る。以前の Rust + GPUI 版の経験も生かせる
- **ファイラは付け替えられる枠にする。** yazi・Dolphin・PRELUDE のフィールド表示など、好きなものを選ぶ(判断 7 のレシピの延長)。最初のフォルダは paths の `files`
  - **判断 14 で見直した**: 自作のファイラとフィールド表示はやめ、ファイラは外のプログラムに任せる(既定は yazi)
- **ウィジェット類は作らない。** バーなどは rice の部品に任せ、PRELUDE は表示用の出口(`prelude watch` の JSON のイベントなど)を出す

### サイドバーで確かめること(試作)
結果は判断 11 の「GPUI の試作で分かったこと」。
- layer-shell(画面の端に場所を予約する)を GPUI で使えるか。だめなら、コンポジタの決まりで浮いた窓を端に固定する → **使える**(場所の予約でほかの窓が寄るかは、全画面でない環境で確かめる)
- 日本語入力(fcitx5。名前の変更など) → **できる**(普通の窓でも layer-shell でも)
- GPU が不調なときの振る舞い → **wgpu の GL(ソフトウェア描画の llvmpipe も)へ自分で切り替わる**

### 対応付け(判断 12 で決定)
- **スペース = コンポジタの作業領域の組、タブ = 作業領域 1 つ、ペイン = 窓 1 つ**。窓と作業領域があるかどうかはコンポジタが持ち、それが何か(どのタブ・ブックマーク・スペースか)はコアが持つ。コアはコンポジタの IPC のイベントで対応表を合わせる
- コンポジタ自身のタブの見た目(Hyprland のグループのバーなど)は隠す。そのための設定の断片は PRELUDE の NixOS モジュールが出す

残りの決めごとは判断 12。

### この PC の rice(2026-11-06)
`nix/rice.nix` に置く(waybar・swaync・タイトルバー・キー配列・fcitx5・鍵の保管庫)。分割は sway の `$mod+b`・`$mod+v` のほか、バーの分割のボタン(ランチャーを分割の向きで開く)でもでき、PRELUDE は結果を読み戻すだけにする。通知とクイック設定は swaync に任せる(2026-11-10。自作の GPUI のパネルは作らない)。PRELUDE の GPUI のバーは作らない(トレイが要り、バーは rice の部品のため)

### ランチャーが入口(2026-11-06)
層 1 のランチャーだけで PRELUDE を使えるようにする。rice が無くても困らないことが条件で、rice とは分けておく。設定・PRELUDE CLI・サイドバーの開閉・分割・閉じるは、ランチャーの COMMANDS から行う。コンポジタのキー(`$mod+b` など)はあってもよいが、それが無いとできない操作を作らない。分割はランチャーが `pane.split`(アプリは `item.open` の `split`)をコアへ頼み、ペインの種類を選べる

サイドバーの幅は「広い」と「細い列」の 2 つで、一番上の PRELUDE の行(つまみ)で切り替える。見た目だけの状態なのでコアには持たせず、サイドバーが `$XDG_STATE_HOME/prelude/sidebar` に覚える(`prelude_proto::sidebar`)。`prelude sidebar toggle`(ランチャーの Toggle sidebar も)はこのファイルを書き換え、サイドバーはそれを見て幅を変える。完全に隠すのは `prelude sidebar hide`(プロセスを止める)だけにする。Electron 版の上のバーの PRELUDE ボタンは、rice のバーにまたがらないよう、サイドバーの中のつまみに移した

### 移行の順番への影響(判断 6)
- 段階 3-a の取り込み(KWin のスクリプトで窓を重ねる)は、コンポジタに窓を並べさせる形に変わる。起動した窓をタブに結び付ける照合(pid・窓のクラス・タイトルの印)はそのまま使う
- 段階 4 は「既定の UI(Slint)」から「サイドバーとランチャー(GPUI)」に、段階 5 は「ファイラの移植」から「ファイラの枠」に、段階 6(`sys/` の移植)は rice に任せる形になる。KDE で Electron 版を使っている間は、今の `sys/` を使い続ける

## 判断 11: UI はすべて GPUI、ランチャー、コンポジタ(決定)

### UI の技術: すべて GPUI(判断 2 を置き換える)
- **Slint は使わない。** PRELUDE の UI(サイドバー・ランチャー・ファイラ)はすべて GPUI で作る。Slint はコードに入っていなかったので、変えるのは設計だけ
- 理由:
  - 付け替えは「部品はトレイト、プログラムはソケット」の 2 段(判断 10)になり、`.slint` を実行時に読む利点が要らなくなった
  - `.slint` には型の決まりを付けられず、部品の抜けが読み込むまで分からない。**UI の部品にも抽象の決まり(トレイト)がある方がよい**。例: ファイラの見せ方はどれも `FilerView` を満たす

    ```rust
    trait FilerView {
        fn render(&mut self, dir: &DirState, cx: &mut Context<Self>) -> impl IntoElement;
        fn on_command(&mut self, cmd: FilerCommand) -> Option<CoreCommand>;
    }
    ```

### GPUI の試作で分かったこと(段階 0。`proto/gpui`)
この PC(Kubuntu・KDE Plasma 6 の Wayland・Iris Xe)で、`proto/gpui`(サイドバーの形の試作)を動かして確かめた。

- **GPUI の入手**: crates.io の `gpui` 0.2.2 には layer-shell が無い。Zed のリポジトリの `gpui`・`gpui_platform` をコミットで固定して使う(描画は wgpu)。ルートのワークスペースには入れず、`cargo test` に巻き込まない
- **ビルド**: 開発用のライブラリが要る(Kubuntu では `pkg-config libxkbcommon-dev libxkbcommon-x11-dev libwayland-dev libfontconfig-dev libfreetype-dev libx11-xcb-dev libvulkan-dev cmake clang`)。NixOS では flake の `nix develop` に書く。初回のビルドは Zed のリポジトリの取得を含めて 30 分ほど、実行ファイルは debug で 700MB
- **layer-shell**: 使える(`WindowKind::LayerShell`)。左・上・下に貼り付け、高さ 0 を渡すと画面の高さいっぱいになる。場所の予約(`exclusive_zone`)は、PRELUDE(Electron 版)が全画面なので、ほかの窓が寄るかはまだ見ていない
- **フォント**: 指定しなくても、漢字・かな・半角カナ・丸数字・絵文字が出る(fontconfig で代わりのフォントを探す)
- **1 万件の一覧**: `uniform_list` で見える行だけを描く。作った 1 万件は 5ms、本物のフォルダ(ファイル 1 万件)の読み込みと並べ替えは 15ms で出る
- **GPU が不調なとき**: 判断 11 で「ソフトウェアでの描画が無い」としていたが、**wgpu には GL があり、自分で切り替わる**。Vulkan(Iris Xe)→ Vulkan が無ければ GL(Mesa)→ さらに `LIBGL_ALWAYS_SOFTWARE=1` で llvmpipe(CPU)。どれも同じに描けた。使った GPU はログに出る
- **日本語入力(fcitx5)**: 普通の窓でも layer-shell のサイドバーでも、変換しながら打てる(変換中の下線・候補の窓・確定)。入力欄は Zed の例(`examples/input.rs`)の `TextInput` をそのまま使った
- **スクロール**: 1 万件の一覧をホイールで動かしてもカクつかない
- **結論**: 段階 4 のサイドバーとランチャーは GPUI で作れる。残る心配は判断 11 の「API が Zed と一緒に変わる」で、固定するコミットを上げるときにまとめて直す

## 判断 13: フィールドのカードはファイラに包含する(判断 14 で取り消し)

> **判断 14 で取り消した。** ファイラを PRELUDE から外し、フィールド表示はやめる。以下は記録として残す。

フィールド表示のカードを、ファイラの外に別の仕組みとして持たない。**ファイラの本体が「開いているフォルダの木」を持ち、カードはその 1 つ 1 つの見せ方** にする。

### 理由
試しに、枠は今のフォルダ 1 つ(`DirState`)だけを持ち、フィールドの部品が別にカードの木を持つ形で書いてみた。カードは `DirState` とほとんど同じもの(フォルダ・中身・カーソル)を持つので、次の無理が出た。
- 枠が今のフォルダを変えた後に、部品が何が起きたかを推測して木を合わせることになる。「閉じる」「兄弟に替える」は推測できず、先に印を渡すことになる
- 今のカード以外の中身が古くなる。コピーや複数選択も今のカードでしか使えない

### 形
```text
枠(Filer)
└ フォルダの木: DirState が親子でつながったもの(今のフォルダの印つき)
   ├ list  の見せ方: 今のフォルダだけを描く(木は 1 段で使う)
   └ field の見せ方: 木を全部カードとして描く。部品が持つのは場所とカメラだけ
```

- カードは「`DirState` への参照 + 場所」。子を開く・閉じる・兄弟に替えるは枠の操作にする
- 読み直しと変化への追従は、枠が木の全部のフォルダに対して行う。選択・コピーは `DirState` の機能なので、どのカードでも使える
- `FilerView::render` が受け取るものは、今のフォルダから「フォルダの木」に変わる。部品は枠と一緒にビルドするので、版の問題は無い(判断 12)
- 配置の計算(`src/fieldlayout.js` の移植)は場所しか見ないので、この形でもそのまま使う

### 順番
- 実装は後回しにする(段階 5-c)。それまで `field` のペインは一覧で出し、上の行に「not yet」と出す
- 今のファイラ(一覧とファイルの操作)は、そのまま動く。先に変えるものは無い

## 判断 14: ファイラを PRELUDE から外す。既定は yazi(決定)

PRELUDE が持つのは「何をしているか」(スペース・ブックマーク・paths)で、ファイルの一覧と操作はその外にある。判断 10 で「ファイラは付け替えられる枠」にしたが、実際には自作のファイラ(`ui/prelude-filer`。約 3,200 行で UI の中で一番大きい)を育てていて、0 章の「ミニマル」とずれていた。**ファイラは外のプログラムに任せ、既定は yazi にする。** フィールド表示はやめる(判断 13 は取り消し)。

### 残すもの・外すもの
| PRELUDE に残す | 外に任せる |
|---|---|
| paths の考え方(`files`・`open`・`save`・`terminal`…) | 一覧の表示・ファイルの操作(コピー・削除・監視) |
| ダイアログのポータル(最初のフォルダを決めるだけ) | 選ぶ画面 |
| ファイラとの約束(レシピの `{path}`、移った先を伝える `prelude pane path`) | ファイラそのもの(`prelude-filer`)とフィールド表示 |

### `.prelude` の中のパスは 2 種類
1. **`[paths]`(何をしているか)**: 変えない。もともとファイラを知らず、使う側(レシピ・ポータル・端末)は `{paths.files}` などの置き換えで受け取るだけ。`files` は「ファイラで最初に開くフォルダ」という名前の 1 項目のまま
2. **ペインの `path`**: ファイラと絡んでいたのはこちら。汎用の欄にする(下)

### ペインの `path` を汎用の欄にする
- どのレシピのペインでも `path`(このペインの場所)を持てる。レシピの `{path}` はペインの `path`、無ければ paths の `files`(今もどの種類にも効いている)
- タブ・ペインの名前は、`path` があればその最後の名前。**コアは `files`・`field` の種類を名指ししない**(今の名指し: `state.rs` のペインの名前とブックマークを開くときの `paths.files` の書き込み、`prelude-proto` のペインの名前)。`files` は `console` と同じ、ただのレシピになる
- `type = "field"` は `files` の別名として読む(古いブックマークも開ける)
- **ブックマークの `path` は「開き始める場所」**。中で移った先は `.prelude` に書かない(判断 5 の「ファイルには使用者が決めたことだけ」。コアはもともと `.prelude` を書き戻さない)。アプリのペインで、Kate が開いているファイルを追いかけないのと同じ
- 移った先は、タブの保存(`~/.local/state/prelude/`)にだけ残る。残すかどうかはファイラ次第で、`prelude pane path [--pane <id>] <フォルダ>`(中身は今の `pane.update` の `path`)を呼べば残る。yazi はプラグイン(フォルダを移ったときのフック)で呼べる。呼ばないファイラは、開き直すと最初の場所に戻る
- ファイラの中の状態(並べ替えの `sort`、`[ui.field]`)は形式から外す。今あるファイルは「知らない項目は無視して残す」(判断 5)でそのまま読め、書き直しは要らない。テストの見本(`test/fixtures/format/full.prelude`)からは、実装のときに外す

### 既定のファイラ: yazi
- 端末の中で動き、キーで操作でき、プレビューとプラグイン(Lua)を持つ。`--chooser-file` で選ぶ画面にもなるので、ファイラとダイアログが 1 つで済む
- 既定のレシピは `files` = `konsole --workdir {path} -e yazi {path}`(窓の名前は `org.kde.konsole`。同じ konsole のペインとは起動したプロセスで見分ける)。端末は `cli`・`console` のレシピと同じ konsole にし、替えるときは一緒に替える
- Dolphin などに替えるのは今と同じく `~/.config/prelude/panes/files.toml`
- yazi は NixOS のモジュール(`services.prelude`)が入れる

### アプリのダイアログ: 選ぶ画面も yazi
- 既定の `chooser.toml` は yazi を使う小さなスクリプト `prelude-choose`(コマンドと一緒に配る)。`{mode}`・`{path}`・`{name}`・`{output}` を受け、`konsole -e yazi --chooser-file {output} {path}` を起動する。選ぶ画面の窓は今と同じく `PRELUDE_DIALOG=1` で浮かせる
- **保存**: yazi には新しい名前を打つ画面が無い。xdg-desktop-portal-termfilechooser と同じやり方にする: 最初のフォルダに保存する名前(`{name}`)の仮のファイルを置き、yazi でそれを選ぶ(名前を変えても、別のフォルダへ移って別の名前にしてもよい)。終わったら仮のファイルを消し、選んだパスを返す。取り消しのときも消す
- 開く(複数を含む)はそのまま。フォルダを選ぶときの操作は実装で確かめる
- **最初のフォルダの優先順を変える**: 「`current_file`(保存し直すファイル)のフォルダ → 今のブックマークの `paths.save` / `paths.open` → アプリが渡した `current_folder` → ホーム」。今はアプリの `current_folder` が paths より先で、アプリが前回のフォルダを渡すと、ブックマークの保存先が効かない(`portal.rs` の `Ask::parse` と `folder_of`)
- ポータルを使わないアプリ(自前のダイアログを出すもの)には、今と同じく効かない

### `prelude-filer` と Electron 版のファイラ
- `ui/prelude-filer` は既定から外したら消す(`FilerView` のトレイトも)。別のリポジトリに移すほどの理由は今は無く、要れば git の履歴から戻せる。`nix/prelude-ui.nix` からも外す
- サイドバーの + の Field、ペインの種類の印の `field` を外す。Folder はそのまま(`files` のレシピを開く)
- Electron 版のフォルダ・フィールドのペイン(`fileops.js`・`src/files.js`・`src/field.js`・`src/fieldlayout.js`)には手を入れず、8-c で Electron 版と一緒に消す

### 実装の順番
1. コア: `files`・`field` の名指しを消す、`field` を `files` の別名にする、`prelude pane path`、ダイアログの優先順
2. 既定のレシピと `chooser.toml` を yazi にする、`prelude-choose`、NixOS のモジュールで yazi を入れる
3. 移った先をコアに伝える yazi のプラグインの例(`docs/rice.md`)
4. `prelude-filer` を消す、サイドバーの Field を外す、テストの見本から `sort`・`[ui.field]` を外す

### 影響
- 判断 10: 「ファイラは付け替えられる枠」は「外のファイラ(既定は yazi)」に、「PRELUDE のフィールド表示」は無くなる
- 判断 11: `FilerView` は例として残すが、実物は消える
- 判断 12: ダイアログの選ぶ画面は yazi
- 判断 13: 取り消し

## 判断 15: PRELUDE は OS の役割を持たない。どの OS・デスクトップにも載る(決定)

PRELUDE が持つのは「何をしているか」(スペース・ブックマーク・paths・履歴)と、それを開く入口(ランチャー)だけにする。デスクトップの外回り・OS の設定・セッション・更新・窓の管理は、OS・デスクトップ・rice の仕事として手放す。手放すことで、PRELUDE は NixOS や sway を前提にしなくなり、ほかの OS・デスクトップにも載せられる。
窓は手放すが、**rice(sway など)・KDE などそれぞれの決まりに合わせる「つなぎ」を差し込める余地は残す**。

### 3 つの層
| 層 | 中身 | 持ち主 |
|---|---|---|
| 本体 | コア(状態とコマンド)、`.prelude`・`space.toml`(`prelude-format`)、ソケットの約束(`prelude-proto`)、`prelude` コマンド、**ランチャー** | PRELUDE。どこでも同じに動く |
| つなぎ | 環境に合わせる差し込み口: 窓(コンポジタ)、アプリのダイアログ、アプリの一覧、外付けの UI(サイドバー) | PRELUDE が既定のものを出すが、どれも無くてよい。入れるかは使用者と環境が決める |
| 環境 | OS、デスクトップ・コンポジタ・rice、バー・通知・ロック、パッケージの管理と更新、どこでも効くキー | PRELUDE ではない |

**つなぎが 1 つも無くても PRELUDE は使える**: ランチャーから、paths(作業フォルダ・最初のフォルダ)を付けてアプリ・URL・フォルダ・ブックマークを開ける。つなぎは、それをその環境でもっと便利にするだけにする。

### 手放すもの
| 役割 | 今 | これから |
|---|---|---|
| デスクトップの外回り(バー・通知・トレイ・OSD・音量・ロック画面・ログイン画面) | Electron 版の `sys/`・`theme/`・`scripts/shell-mode.sh` など | 作らない。Rust 版へは移さず、8-c で Electron 版と一緒に消す(判断 10 の rice に任せる、を全部に広げる) |
| OS の設定 | `nix/configuration.nix`・`hardware-configuration.nix`・`rice.nix`・`claude-desktop.nix`・`open-pdf-studio.nix`・`install-from-live.sh`・`copy-home.sh` | この PC の設定で、PRELUDE の設計ではない。別のリポジトリ(この PC の dotfiles)へ移す。移すまでは `nix/` に置いたまま、PRELUDE の一部としては扱わない |
| セッションの起動 | `nix/module.nix` が sway のセッションでコアを起動・停止し、環境を渡す | コアはふつうのユーザーのサービス(または自動起動)で、どのセッションでも同じに動く。sway のセッションに合わせる断片は、sway のつなぎの「例」にする |
| 更新 | `release.sh`・`sys/update.js` | OS のパッケージの管理に任せる(Nix・ディストリビューションのパッケージ・自分でビルド)。PRELUDE は版のタグを打つまで |
| 乗る先の OS | 判断 9「NixOS」 | PRELUDE の前提ではなくなる。**作者の PC が NixOS** というだけにする(判断 9 は格下げ) |
| どこでも効くキー | 判断 1-b ③ | 環境のキーの設定から `prelude-launcher`・`prelude …` を呼ぶ。PRELUDE はキーを横取りしない(今と同じ) |

### 残すもの: ランチャー
- **ランチャーは本体に入れる**(判断 10 の層 1 を「ほぼ必須」から本体へ)。PRELUDE を使う入口で、つなぎが無い環境でもこれだけで使える
- 候補と点数はコア(`item.list`)、開くのもコア(`item.open`)。ランチャーは見せて選ぶだけ(今と同じ)
- 窓の出し方は環境に合わせる: layer-shell があればそれ、無ければ浮いた普通の窓。fuzzel などに替えられるのも今と同じ
- 分割で開く(`split`)は、窓のつなぎが分割できるときだけ出す

### 窓: 「つなぎ」に任せ、合わせる余地を残す
- コアは窓を持たない。**タブは「開いている作業」(どのブックマークを開いたか・何を開いたか)という論理の単位** にし、作業領域・仮想デスクトップ・タブのどれに当てるかはつなぎが決める。判断 12 の「タブ = 作業領域」は、sway のつなぎの決めごとになる
- `Compositor` のトレイト(`compositor.rs`)をつなぎの差し込み口にする。つなぎは、できることを段で名乗る:

  | 段 | できること | 例 |
  |---|---|---|
  | 0. 無し | アプリを起動するだけ。置き場所は環境に任せる | どの環境でも |
  | 1. 並べる | ブックマークを開くときに `[layout]` のとおりに並べる | |
  | 2. 読む | 今の並びを読む(タブの保存・ブックマークの配置を書くとき) | |
  | 3. 追う | 窓の動き・PRELUDE を通さずに開いた窓を追いかけて、コアの状態に合わせる | 今の sway(`sway.rs`) |

- コアは段 0 だけで成り立つように作る。上の段は、つなぎがあるときだけ使う。今の `--no-embed`(アプリも起動しない)とは別に、「つなぎ無し = 起動はする」をふつうの動き方にする
- 既定で出すつなぎ: **sway(SwayFX)**(今の `sway.rs`。段 3)と **KWin**(今の `embed.rs`・`embed.js`)。判断 12 の「移行が終わったら KWin の裏側を消す」は取り消し、KDE で使う人のつなぎとして残す(保守が重くなったら段を下げる)。Hyprland・GNOME などは、要る人がつなぎを足せる
- `[layout]` は今の形のまま(つなぎが無ければ「開くものの一覧」として読む)
- 窓の持ち主を見分ける `/proc`(`procs.rs`)や窓の印は、つなぎの中の事情として扱う

### ほかのつなぎ
- **アプリのダイアログ**(`portal.rs`): xdg-desktop-portal のある環境だけのつなぎにする。コアは「最初のフォルダ」(`dialog_folder`)を答えるだけで、ポータルはコアに聞く小さな別のプログラムに分ける。入れなければ、アプリのダイアログは環境のまま
- **アプリの一覧**(`apps.rs`・`xdg.rs`): 今は XDG の `.desktop`。Linux のつなぎとして扱い、ほかの OS では別のものに差し替えられるようにする
- **外付けの UI**(サイドバー): 今と同じく任意。layer-shell の無い環境では出さないか、浮いた窓にする
- **Web**(Chromium と CDP): 本体に残す(CDP はどの OS でも同じ)。窓の部分だけ窓のつなぎを通す

### ほかの OS について
- まずは Linux のいろいろなデスクトップ(sway・KDE・つなぎ無し)で同じに動くことを目標にする
- macOS・Windows は今は作らないが、道をふさがない。本体に OS に依存するものを入れない: 設定・状態・ソケットの場所は 1 か所で決める(今は XDG の決まり)、`.desktop`・`/proc`・D-Bus はつなぎの中だけにする。GPUI(ランチャー)は macOS・Windows でも動く

### 実装の順番
1. コア: つなぎ無しでも起動する(段 0)、タブを論理の単位にして作業領域との対応を sway のつなぎへ寄せる、つなぎが段を名乗る
2. ポータルを別のプログラムに分ける。アプリの一覧を差し替えられる形にする
3. `nix/`: PRELUDE のパッケージと、小さなモジュール(コアのサービス・任意のつなぎ)だけにする。この PC の設定は別のリポジトリへ(リポジトリは使用者が作る)
4. 8-c で Electron 版と一緒に `sys/`・`theme/`・シェル関係の `scripts/` を消す(KWin のつなぎは残す)

### 影響
- 判断 1: 図のコアから「OS: KWin・D-Bus(通知・トレイ・OSD・音量)」を外す。窓とダイアログはつなぎ
- 判断 1-b ②: ペインの場所はつなぎ(無ければ環境)が決める
- 判断 9: PRELUDE の前提ではなく、作者の環境の記録になる
- 判断 10: 層 1 のランチャーは本体へ。層 2(外付けの UI)はつなぎ、層 3(rice)は環境
- 判断 11: 「コンポジタは SwayFX に決定」は作者の環境の選択。PRELUDE はつなぎで合わせる
- 判断 12: 「タブ = 作業領域」は sway のつなぎの決めごと。「KDE を外す」は取り消し
- 判断 14: 既定のファイラ(yazi)は本体の既定のレシピのまま。ダイアログ(yazi)はダイアログのつなぎの既定になる
- 段階 6・8: 段階 6 は「rice に任せる」から「環境に任せる」に、8-c で消すのは Electron 版とシェル関係だけ(KWin のつなぎは残す)
